# Малеча — CRM для дитячого садочка

Next.js 16 (App Router) + React 19 + Tailwind CSS 4 + PostgreSQL.

## Вимоги

- Node.js `>=20.9.0`
- Docker (для локальної бази)

## Запуск

```bash
npm install
npm run db:up
cp .env.example .env.local          # і заповни NEXTAUTH_SECRET
npm run db:migrate
npm run user:create -- admin@example.com <пароль> "Ім'я" admin
npm run dev
```

Додаток відкриється на http://localhost:3000, база — на `localhost:5433`
(див. `docker-compose.yml`).

## Оплата колективу

Три способи нарахування, обираються в картці працівника:

| Тип | Розрахунок | Що відмічають у календарі |
| --- | --- | --- |
| Місячна ставка | ставка ÷ робочі дні × оплачувані | стан дня |
| За день | ставка × оплачувані дні | стан дня |
| За заняття | ставка × кількість занять | заняття за день, кожне з власною приміткою |

### Стани дня

День має один із чотирьох станів або лишається невідміченим; клік по клітинці
перебирає їх по колу:

| | Стан | Оплачується |
| --- | --- | --- |
| ✓ | Відпрацьовано | так |
| × | Не відпрацьовано | ні |
| В | Оплачувана відпустка | так |
| О | Оплачуваний вихідний | так |
| · | Не відмічено | ні |

**Оплачувані дні** = відпрацьовані + відпустка + оплачувані вихідні. Саме до
них застосовується місячна й поденна ставка, тож відпустка не зменшує зарплату.

Ліміти задаються **в налаштуваннях працівника**, але періоди в них різні:

| Ліміт | Період | Як рахується використане |
| --- | --- | --- |
| Відпустка | днів на календарний рік | усі дні відпустки за рік, у якому вибраний місяць |
| Оплачувані вихідні | днів на місяць | дні вихідних лише у вибраному місяці |

Тому вересневий день відпустки видно в річному підсумку й тоді, коли відкрито
серпень, а вихідні щомісяця починаються з нуля. У картці працівника видно
«використано / залишилось» для кожного ліміту.

Ліміт нічого не блокує: він показує баланс, а не забороняє відмітити зайвий
день.

Заняття зберігаються по одному запису на заняття (`lessons`), тому в один день
їх може бути скільки завгодно або жодного, і примітка належить конкретному
заняттю, а не дню.

### Два способи дивитися на місяць

Розділ «Колектив» має перемикач **Список / Табель**:

- **Список** — рядок на працівника зі ставкою, днями й нарахованим; клік
  відкриває картку з календарем, виплатами й редагуванням ставки.
- **Табель** — матриця «колектив × дні місяця». Відмічати можна прямо в
  клітинці: у погодинного персоналу клік перебирає стани дня, у вчителів на
  занятті — відкриває список занять того дня з примітками. Під іменем видно
  залишок лімітів — `В використано/ліміт` для відпустки за рік і
  `О використано/ліміт` для оплачуваних вихідних за місяць.

Коли відмітка виводить за ліміт, працівник підсвічується червоним, а вгорі
сторінки з’являється попередження. Воно нічого не скасовує: ліміт показує
баланс, а не забороняє відмітити зайвий день.

### Нараховано vs видано

Табель дає **нараховане** — те, що садочок винен працівнику. Реальні виплати
відмічаються окремо в `salary_payments`: аванс і остаточний розрахунок, кожна
з датою й приміткою. У картці працівника видно «нараховано / видано / залишок».

У виплати дві дати: `month` — платіжний місяць, який закривають, і `paid_at` —
коли гроші фактично видали. **Усі підсумки згруповані за `month`**, тож
серпнева зарплата, видана 3 вересня, лишається в серпні на всіх екранах.
`paid_at` зберігається як фактична дата видачі й показується у картці
працівника.

## Звіти

Перемикач **За рік / За місяць**. Обидва режими показують ту саму помісячну
діаграму за рік — у місячному режимі обраний стовпчик підсвічується, щоб було
видно, як місяць виглядає на тлі решти. Підсумки, структура витрат і виплати
звужуються до обраного періоду.

Кількість дітей і наповнюваність груп рахуються **за період звіту**, а не
станом на сьогодні: дитина потрапляє в місяць, якщо вікно `enrolled_at …
left_at` перетинається з ним. Порожня дата означає «невідомо» й межу не
звужує, тож діти, заведені до появи цих полів, зі звітів не зникають. Поруч
видно, скільки за той самий період прийшло й вибуло.

Місячний звіт дає більше по колективу: **нараховано / видано / залишок**.
Нарахування вимагає перерахунку табеля, тож для одного місяця це дешево, а за
рік показується лише видане.

Усе агрегується в SQL через `GROUP BY` — дванадцять помісячних знімків
означали б десятки звернень до бази заради тих самих сум.

Дохід і зарплати групуються за платіжним місяцем, інші витрати — за датою
операції, як і на сторінці «Доходи й витрати».

## Черга

Заявки на місце живуть у `waitlist`: дитина, **одна** контактна особа з
телефоном і поштою, побажання щодо групи (`preferred_group_id`, `NULL` —
будь-яка) та щодо початку (`desired_from`, перший день бажаного місяця).

Статуси: `waiting` → `invited` → `enrolled` / `declined`; змінюються прямо в
рядку.

Заявки згруповані **за віковою категорією**. Категорії заводяться окремо —
кнопка «Вікові категорії» на сторінці черги — і кожна охоплює **діапазон років
народження** (`age_categories.from_year … to_year`, обидва включно), бо в одну
групу садочок бере дітей кількох років. Категорії показуються від найстарших
дітей до наймолодших; заявки, чий рік не потрапив у жодну категорію або в яких
немає дати народження, йдуть окремим блоком у кінці. Якщо рік підходить двом
категоріям, виграє старша.

Усередині категорії заявки нумеруються з 1 за датою подання — це місце в черзі.
Номер рахується по всій черзі, а не по відфільтрованому списку, тож фільтр за
статусом чи пошук нікого не перенумеровують. Заголовок «Подано» перемикає
напрямок сортування; номери при цьому лишаються тими самими.

Зарахування з черги поки не переносить дані в `children` автоматично — дитину
треба завести в розділі «Діти та групи» окремо.

## Групи

Назву та вікову категорію групи можна змінити — олівець у куті картки на
сторінці «Діти та групи». Діти прив'язані до групи за `group_id`, а не за
назвою, тож перейменування нічого не рве й не потребує каскаду. Активний
фільтр списку зберігає назву, тому після перейменування він переїжджає на нову
сам, інакше список став би порожнім.

## Дні народження

На головній сторінці — панель із днями народження дітей і персоналу на
**сьогодні та наступні три дні**. На відміну від решти дашборда вона не
залежить від вибраного місяця: «найближчі» рахуються від поточної дати
сервера.

Вікно будується як чотири конкретні дати, а пошук іде за `MM-DD`, тож перехід
через межу місяця чи року окремого випадку не потребує. Дата народження
працівника задається у формі «Редагувати працівника», дитини — у картці
дитини; обидві необов'язкові.

## Доходи й витрати

Дохід у садочку рівно один — місячна оплата, і вона вже є в `payments`.
Тому вручну заводяться **тільки витрати**: таблиця `transactions` не має
поля типу, кожен її рядок є витратою.

| | Звідки береться |
| --- | --- |
| Дохід | оплати батьків (`payments`) — фактично отримані |
| Витрати: зарплата | `salary_payments` — фактично видані |
| Витрати: решта | `transactions`, вводяться вручну |

І дохід, і витрати — це рух грошей, а не зобов'язання: у балансі стоїть
отримане й видане.

Зарплати виведені **окремою таблицею** над списком витрат: рядок на кожного
працівника з нарахованим, виданим, залишком і прогресом видачі, а над нею —
підсумок «видано / залишилось / нараховано». Ручний список витрат містить лише
те, що вводили вручну.

Категорія — вільний текст із підказками (продукти, оренда, комунальні тощо).
Якщо колись знадобиться облік іншого доходу — гранту чи донату, — це окрема
таблиця або повернення поля типу.

## Філії та ролі

| Роль | Що бачить | Що може |
| --- | --- | --- |
| Власник (`admin`) | усі філії, усі облікові записи | створювати філії, призначати керуючих, міняти ПІБ будь-кому |
| Керуючий (`manager`) | лише свою філію (`users.branch_id`) і власний обліковий запис | працювати в межах філії, міняти власне ПІБ |

**Вибір філії з'являється не завжди.** Поки філія одна і власник керує нею
сам, вибору немає ніде — він виникає, щойно з'явиться друга філія або
керуючий. Це рішення живе в `lib/scope.ts` (`canSwitch`), а не в кожній
сторінці окремо.

Кожен запит проходить через `resolveScope()`, який визначає філію з сесії:
керуючому вона нав'язується, і параметр `?branch=` від нього **відхиляється з
403**, а не мовчки ігнорується — щоб помилка спливла, а не показала чужі дані.
Власник може перемикатися, але тільки між наявними філіями.

Керування філіями — сторінка `/branches`, у навігації її бачить лише власник.

Оплати й виплати не мають власного `branch_id`: перші належать філії через
дитину, другі через працівника, тож у звітах вони фільтруються джойнами.

## Доступ

Усе, крім `/login` та `/api/auth/*`, закрите. Неавторизований візит на сторінку
редиректить на `/login`, запит до API отримує `401`. Правило одне — [proxy.ts](proxy.ts).

Сесії — JWT (next-auth, провайдер credentials), паролі — bcrypt.

`admin` і `manager` розводяться по правах у `lib/scope.ts` та `/api/settings`;
`teacher` поки що прирівняний до `manager`.

## Налаштування

`/settings` є в обох ролей і редагує **ПІБ**. Власник бачить там усі облікові
записи й може виправити ПІБ будь-кому, керуючий — тільки власний запис: чужі
акаунти до нього навіть не доїжджають із сервера, а спроба зберегти чуже ПІБ
повертає `403`, а не мовчки підміняє id на власний.

Роль сервер бере з бази, а не з токена: її могли змінити на сторінці «Філії»
вже після входу. Ім'я, навпаки, живе в токені — тому після збереження сторінка
викликає `useSession().update({ name })`, інакше сайдбар показував би старе ПІБ
до наступного входу.

Пошту й роль у налаштуваннях не змінити: перша — ідентифікатор входу, другу
задає власник, призначаючи керуючого на філію.

Там же — блок філії з **назвою та адресою**. Редагує їх власник; керуючий
бачить свою філію, але поля в нього неактивні, бо філії — робота власника.

## Кольорові схеми

Чотири пастельні схеми: **зелена** (типова), **синя**, **червона**, **жовта**.

| Хто | Що може |
| --- | --- |
| Власник | свою особисту схему **і** схему кожної філії окремо |
| Керуючий | схему своєї філії — **лише поки її не задав власник** |

Замок тримає `branches.theme_by_owner`: за самим `theme` не видно, хто його
виставив. Власник, зберігаючи схему філії, піднімає прапорець, і керуючий
далі бачить перемикач неактивним. «Типова» скидає схему разом із прапорцем —
філія знову вільна.

Яку схему бачить конкретна людина, вирішує `resolveTheme()` у
[lib/theme.ts](lib/theme.ts): у власника перемагає особиста схема (він
дивиться на кілька філій одразу, і перефарбовування на кожному перемиканні
тільки заважало б), у керуючого — схема його філії.

Схема ставиться атрибутом `data-theme` на `<html>` **на сервері**, щоб сторінка
не блимнула типовою й лише потім перефарбувалась. Через це рендер усіх сторінок
став динамічним — за автентифікацією тут і так усе.

У CSS схема перевизначає **тільки акцентні змінні** (`--accent`, `--accent-soft`,
`--accent-ink` тощо). Нейтральні тони й усе, що несе зміст — помилка, попередження,
відпустка, оплачуваний вихідний, заняття — однакові в усіх схемах, інакше
червона схема зробила б «не відпрацьовано» невідрізнюваним від решти.

Після збереження сторінка викликає `router.refresh()`: кольори малює серверний
layout, і без цього нова схема з’явилася б аж на наступному переході.

| Змінна | Опис |
| --- | --- |
| `NEXTAUTH_SECRET` | Підпис JWT-сесій, обов'язкова |
| `NEXTAUTH_URL` | Базовий URL, напр. `http://localhost:3000` |

## Деплой на Railway

Сервіс збирається з `Dockerfile` (`railway.json` вказує на нього явно), образ
standalone-збірки Next. Один інстанс — див. застереження про міграції нижче.

1. **Postgres** — плагін Railway в тому ж проєкті.
2. **Змінні сервісу:**

   | Змінна | Значення |
   | --- | --- |
   | `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` — приватною мережею |
   | `NEXTAUTH_SECRET` | `openssl rand -base64 32` |
   | `NEXTAUTH_URL` | `https://${{RAILWAY_PUBLIC_DOMAIN}}` |
   | `BOOTSTRAP_ADMIN_EMAIL` | пошта власника |
   | `BOOTSTRAP_ADMIN_PASSWORD` | його пароль |

3. **Деплой.** Після першого вдалого запуску прибери обидві `BOOTSTRAP_*`,
   щоб пароль не лежав у налаштуваннях сервісу.

### Міграції

Накочуються **на старті сервера** — `register()` в [instrumentation.ts](instrumentation.ts)
викликається один раз на інстанс і мусить завершитись, перш ніж сервер почне
приймати запити. `drizzle-kit` тут не годиться: він у devDependencies і читає
`drizzle.config.ts`, а в продакшн-образі немає ні того, ні того, — тож ті самі
міграції з `drizzle/` накочуються програмно, тим самим драйвером, що й
застосунок.

Якщо міграція впаде, застосунок не підніметься. Це навмисно: працювати на
схемі, якої код не очікує, гірше, ніж не стартувати зовсім.

**Розраховано на один інстанс** (`numReplicas: 1`). Кілька реплік, що
стартують одночасно, наввипередки накочували б ту саму міграцію — для цього
знадобився б окремий крок деплою.

### Перший власник

З інтерфейсу обліковий запис не заводиться, тож свіжий деплой упирався б у
глухий кут: увійти нікому. `BOOTSTRAP_ADMIN_EMAIL` і `BOOTSTRAP_ADMIN_PASSWORD`
заводять власника на старті — але **лише поки таблиця користувачів порожня**.
Це саме початкове заведення, а не чорний хід: щойно власник є, змінні нічого
не роблять і нікого не перезаписують.

Далі акаунти додаються скриптом із консолі сервісу:

```bash
node scripts/create-user.mjs пошта пароль "ПІБ" manager
```

### Healthcheck

`/api/health` — єдиний публічний маршрут, окрім `/login` та `/api/auth/*`.
Проба свідомо поверхнева: відповідає на питання «процес живий», а не «база на
місці». Якби вона ходила в базу, коротка недоступність Postgres валила б увесь
деплой, хоча застосунок цілком здатний показати сторінку входу зі своєю
помилкою.

## Міграція зі старої схеми

Перша версія зберігала дані в денормалізованих таблицях `ui_*`, де гроші й вік
лежали як підписи для інтерфейсу (`"12 500 ₴"`, `"4 роки"`). Перенесення в
нормалізовану схему робить `scripts/import-ui-data.sql` — одноразово, після
`npm run db:migrate`:

```bash
docker exec -i malecha-postgres psql -U malecha -d malecha < scripts/import-ui-data.sql
```

Старі `ui_*` таблиці лишаються в базі як резервна копія й більше нікуди не
підключені — їх можна видалити, коли переконаєшся, що все на місці.

## Відомі борги

- Розрахунок зарплати за місячною ставкою не враховує державні свята.
- Витрати й виплати редагуються лише додаванням і видаленням: змінити наявний
  запис не можна.
- Роль `teacher` зберігається, але прав від `manager` поки не відрізняє.
- Червона схема робить акцент близьким до кольору «не відпрацьовано» в табелі;
  відрізняються вони насиченістю, а не тоном.
- Обліковий запис створюється лише скриптом `npm run user:create`; з інтерфейсу
  його не завести.
